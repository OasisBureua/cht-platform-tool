1Summary

CHM (Community Health Media) connects oncology healthcare professionals (HCPs), key and digital opinion leaders (KOLs/DOLs), and pharma sponsors through live CME-style programs, a clinical conversation library, podcasts, and paid participation. The CHT platform is the product that delivers this: a public marketing and catalog site, an authenticated member app for HCPs, and an admin console for CHM operations.

The beta is the first release where the whole loop runs end to end on CHT-owned infrastructure: an HCP discovers a program, registers, attends in Zoom, completes a survey, gets paid, and CHM reports the outcome back to the sponsor. This document defines what the beta must do, how we will measure it, and what is explicitly deferred.

2Problem and goals

Problems today

  • Fragmented tools. Registration, attendance, surveys, payouts and reporting lived across Zoom, JotForm, Bill.com and spreadsheets, with manual reconciliation between them.
  • Identity owned elsewhere. End users authenticated against MediaHub GoTrue, coupling CHT sign-in to a separate system and blocking MFA and compliance controls.
  • Slow sponsor reporting. Executive reports were assembled by hand or through a synchronous endpoint that timed out, and HTML output was not client-ready.
  • Payout friction. Bill.com sessions, vendor setup and paper checks slowed honoraria and created support load.

Beta goals

G1 · One loop

Registration → attendance → survey → payment → report runs without manual hand-offs for a standard program.

G2 · Trusted identity

All users on Cognito with MFA available; admin actions audited; no secrets or tokens in logs.

G3 · Fast, safe payouts

Eligible HCPs are paid by ACH through Stripe Connect with tax details collected in onboarding.

G4 · Sponsor-ready reporting

Admins generate a printed PDF executive report for any campaign in minutes, without seeing raw HTML or storage URLs.

Non-goals for beta

  • Native mobile apps (responsive web only).
  • Self-serve sponsor portal (sponsors receive PDFs; no sponsor log-in in beta).
  • Paper checks or non-US payouts.
  • Accredited CME certificate issuance beyond the existing certificate worker.

4Beta scope

In scope

  • Public site, catalog, KOL network, podcast network
  • Join, login, Google sign-in, MFA, profile completion (NPI)
  • Webinars and CHM Office Hours: register, multi-register, in-app Zoom, approvals
  • Native intake and post-event surveys with analytics
  • Honoraria via Stripe Connect (ACH) with admin Pay-now
  • Admin console: programs hub, schedulers, users, HCP explorer, payments, audit log, Zoom recordings, campaigns funnel
  • Reports console: campaign links, analytics report, executive PDF reports
  • Chatbot (CHM assistant) for members

Out of scope / deferred

  • Sponsor log-in and self-serve dashboards
  • Paper checks, international payouts
  • HTML report delivery (PDF only)
  • Report version history UI beyond regenerate (v1…v3)
  • Native mobile apps
  • MediaHub move onto CHT ECS (roadmap Phase 4)
  • Catalog Redis cache (roadmap Phase 4e)

7Reports console (new)

The Reports console (/admin/reports, formerly /admin/content-hub) is where CHM admins set up sponsor campaigns, connect their data, and produce reports. It is backed by the Content Hub for campaign data and by the cht-reports pipeline for executive PDFs. Old /admin/content-hub links redirect.

The reports API (CPR-30) is merged. The admin UI (CPR-27: program linking, report history, notify picker, route rename) is on dev and marked In beta until it merges.

7.1 User flow

  1. Create a campaign in the Create report wizard: type (analytics or executive PDF), campaign details, data connection (platform CSVs, CHT feedback survey), validation.
  2. Link programs on the campaign's Programs tab so Zoom sessions, attendance and surveys from Platform are included.
  3. Generate on the Reports tab: pick a 30, 60 or 90-day window and sources (HubSpot, LinkedIn, Meta, YouTube, Livestream, Zoom sessions, Surveys), optionally choose admins to email.
  4. Track and download: the request returns immediately; status moves from queued to ready in Report history; download the printed PDF.
  5. Regenerate with optional instructions (up to 2,000 characters), at most three times per report.

8Non-functional requirements

AreaRequirement
SecurityMFA available to all users and required for admins before launch. httpOnly, secure session cookies. Helmet security headers and HSTS in production. Admin API docs gated by admin session.
Secrets and loggingTokens, client secrets and Authorization headers are never logged. Logs are structured JSON without emojis. Success and failure of integrations may be logged.
Service-to-servicePlatform and Content Hub authenticate with Cognito client credentials and least-privilege scopes (for example hub/reports.read, platform/export.read).
PrivacyNo patient data (PHI) is collected. HCP PII (NPI, contact, tax details) is limited to what programs and payouts need; tax details are held by Stripe, not CHT.
AuditabilityAdmin actions, report requests and payment actions write audit log entries.
PerformancePublic pages interactive in under 3 s on broadband; API p95 under 800 ms for reads excluding upstream calls; report requests return in under 1 s.
AvailabilityProduction on ECS Fargate behind an ALB with health checks; RDS backups and documented disaster recovery.
AccessibilityWCAG 2.1 AA as the target: visible labels, keyboard access, focus rings, announced errors, 16 px minimum input text on mobile.
BrowsersLatest two versions of Chrome, Safari, Edge and Firefox; iOS Safari and Android Chrome.
Quality gatesTypecheck, lint and unit tests pass for backend and frontend before merge; deploys go dev, then testapp, then production.

Launch checklist

  • All P0 requirements shipped and verified on testapp.
  • Stripe cutover complete for the environment; legacy check users notified to re-onboard.
  • Admin accounts enrolled in MFA; audit log reviewed.
  • Report pipeline processing jobs, with PDFs under reports/ and Platform read access to the artifacts bucket.
  • Support path and FAQ published for sign-in, MFA, payouts and surveys.
  • Incident response and disaster recovery runbooks current.
