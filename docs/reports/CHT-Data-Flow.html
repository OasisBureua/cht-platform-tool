1Summary

The system has 35 flows in six groups: capture into Platform, Platform outbound, Content Hub ingestion, the report pipeline, Companion, and delivery. The report pipeline is the most robust: it uses SQS with three attempts, a dead-letter queue, a timeout sweeper and idempotent S3 keys. The weakest flows are the ones that feed it. Several of them are fire-and-forget, manual, or switched off in production.

Prod Hub has no scheduled refresh

Content Hub's weekday export ingest (platform_export_ingest) and S3 transcript ingest (vtt_object_ingest) run in dev only. In prod, Hub refreshes Platform data only when Platform triggers it: on campaign link, first transcript pull, Generate, or Refresh data.

Transcripts depend on a manual pull

Zoom recordings and transcripts reach S3 only when an admin clicks Sync or Pull. Reports wait up to 180 minutes for a recent session's transcript, then fail with a "transcript did not arrive" message.

Fire-and-forget flows can lose data silently

HubSpot contact sync, the Hub HCP roster sync and the background export-ingest triggers only log warnings on failure, with no retry. HubSpot sync even reports success when it fails.

Some webhooks acknowledge failures

The Jotform webhook returns 200 when processing fails, so Jotform never retries. The Zoom webhook returns 200 on an invalid signature and skips verification when the signature header is missing.

Queues are protected but not all monitored

Platform's payment, email and scheduled-job queues have dead-letter alarms. The cht-reports request queue has a dead-letter queue but no alarm. Platform's stale-report sweeper is the only signal for a stuck report.

Ownership is clear except at the edges

Each repo owns its own flows. Post statistics (ops-console and MediaHub) and the Zoom, YouTube, LinkedIn and HubSpot APIs are external, so their freshness and retry behaviour are outside our control.

5Failure-handling patterns

PatternFlowsBehaviourVisibility
Queue with retry and DLQA10, A12, C8, D1–D5Message is left on the queue on error, redelivered up to 3 times, then moved to the dead-letter queue. Bad messages are deleted at once.DLQ alarms on Platform queues; none on the reports queue.
Bounded retry in codeA5, D4, D6Fixed attempts with backoff (Bedrock 2 attempts, ready callback 3 attempts, Zoom 404 retried with the UUID).Logs.
Best-effort, then continueA2, C1 (on Generate), B3The failure is logged and the main action continues with older data (stale warehouse, cached HubSpot).Flags such as warehouseSync=failed and dataSource.
Fire-and-forgetB1, B2, C1 (link, transcript)No retry and no outbox. A failure means the data is missing until the next trigger.Warning logs only.
Acknowledge and dropA1 (bad signature), A7Returns 200 to the sender, so it never retries.Logs only.
Manual recoveryA5, A6, C3–C5, D3An admin re-runs the import, pull, sync or upload, or generates the report again.Job and sync status tables, report last_error.
Fail closedE1 rate limiterReturns 503 when Redis is down instead of serving without limits.Error response.
Timeout sweeperD7Marks stuck reports failed and frees the lock.Report status in Platform.
