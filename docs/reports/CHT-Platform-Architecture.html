Community Health Media · CHT Platform

Technical Architecture

How the CHT platform is built and run: frontend, backend, database, authentication, APIs, storage, third-party services, environments and external dependencies.
At a glance
  • React single-page app on S3 + CloudFront, with /api served from the same domain through an ALB.
  • NestJS API and a Python worker on ECS Fargate, deployed by Terraform from GitHub Actions.
  • PostgreSQL 15: Aurora Global in production (us-east-1 writer, us-east-2 reader), RDS on dev.
  • Amazon Cognito for member and admin sign-in (MFA, Google) and for service-to-service tokens with Content Hub.
  • Two environments in one AWS account: Dev (devapp.communityhealth.media) and Platform / production (testapp.communityhealth.media, alias app.communityhealth.media).

1Description

The CHT platform is the web product behind Community Health Media. It serves three audiences from one codebase and one domain per environment:

  • Public site: marketing pages, the clinical conversation catalog, the KOL network, podcasts and upcoming programs.
  • Member app (/app): HCPs register for webinars and office hours, attend in Zoom, complete surveys, get paid honoraria, and watch content.
  • Admin console (/admin): CHM staff schedule programs, approve registrations, manage surveys, users and payments, review audit logs and Zoom recordings, and generate sponsor reports.

The platform owns identity, programs, registrations, attendance, surveys and payments. Catalog content, KOL data and campaign analytics come from the separate Content Hub service. Executive PDF reports are produced by the separate cht-reports pipeline.

2Frontend

AspectDetail
FrameworkReact 19 single-page app, TypeScript, built with Vite 7
RoutingReact Router 7 with lazy-loaded route chunks; public, /app (member) and /admin trees with auth and role guards
DataTanStack React Query 5 over an Axios client; cookies sent with every request (withCredentials); polling for long-running jobs such as reports
UITailwind CSS 3, shared kit in components/ui (Button, Field, Chip, SegmentedControl) and admin patterns (section cards, alerts, status badges); Lucide icons; Recharts for analytics
Payments UIStripe Connect embedded components (@stripe/connect-js) for payout onboarding
ZoomMeeting SDK Client View 5.1.4 loaded from the Zoom CDN inside a same-origin iframe (/zoom-embed.html). CloudFront sends Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: credentialless so live video works.
Bot protectionGoogle reCAPTCHA v3 on join and login when keys are configured
QualityESLint (React Compiler rules), tsc, Vitest unit tests; all run in CI before deploy
HostingStatic build synced to S3 and served by CloudFront; hashed assets cached long-term, index.html and zoom-embed.html uploaded separately; CloudFront invalidation after each deploy

Because the SPA and API share one origin, session cookies are first-party and no cross-origin CORS is needed for the browser. The API also exposes Content-Disposition so downloaded files (for example report PDFs) keep friendly names.

3.2 Worker (chm-worker)

AspectDetail
RuntimePython 3.11 (slim container), boto3, SQLAlchemy with psycopg2, ReportLab and Pillow
ConsumersSQS queues for email (SES), payment (honorarium payouts) and CME (certificate PDFs to S3), plus a scheduled jobs queue
ReliabilityEach queue has a dead-letter queue with a CloudWatch alarm; health check script for ECS
SchedulesEventBridge rules: session reminders (every 12 hours on dev, every 6 hours in production) and, in production, a Bill.com MFA reminder every 20 days

3.3 Key flows

  1. Program to payment. Admin schedules a program (Zoom meeting or webinar created by API) → HCP registers and is approved → Zoom webhooks and in-app SDK events record attendance → HCP submits the post-event survey → backend checks eligibility and queues a payment → worker pays out and updates status.
  2. Executive report. Admin requests a report → backend writes state to DynamoDB, sends a message to the report queue and returns 202 → cht-reports pulls Content Hub and Platform data (via the M2M export endpoint), renders a PDF to S3 → backend streams the PDF to the admin without exposing the S3 location.
  3. Catalog. Backend reads Content Hub public and admin APIs with an M2M Bearer token, caches results in Redis (production, 1 hour), and serves them to the SPA.

12Open items

To resolve
  • Reports in production. The report table, queue and bucket are configured for dev only. Production values must be added to the platform Terraform variables before reports go live there.
  • MFA enforcement. Cognito MFA is optional in both environments. Decide when to require it, starting with admins.
  • Stripe cutover. Production still has Bill.com reminders enabled. Remove them after the Stripe cutover, and retire JotForm once legacy programs close.
  • DR compute. The us-east-2 backend is deployed manually and API traffic is not routed there. Schedule and document a failover test.
  • Docs drift. docs/engineering/architecture.md lists React 18, integrations.md still describes GoTrue auth, and deployment.md describes older production triggers. Update them to match this document.
